# Browser delivery and the global input tap

Stage79 tested the browser Playwright path against an owned local Chrome tab.
The click changed an authored green witness to magenta and its page event counter
reached seven after a click/key operation. Across that interval, the recorder's
sampled healthy global tap callback count stayed at four. A native CUA key
positive control through the same listener then raised it to eight. Two native
app-local key timestamps/keycodes match the retained source.

The callback counter increments before per-recording event filtering in
`InputTimeline.admit`. This zero delta is more informative than an empty target
query alone. It remains one sampled provider case, with healthy listener states
at observations, no observed fault/overflow and no universal completeness proof.
Do not infer physical timing, actor identity or continuous listener state.

The browser read-only evaluation scope did not expose `window.fixtureEvents`,
although the DOM counter updated. Browser event types, trust and per-key delivery
were therefore not independently verified. An accepted key call and focused
textbox do not prove every key event. The combined browser operation's typed
verification remains unknown; the observed click and counter are narrower proof.
The fixture now renders a bounded last32-event metadata block in its own DOM for
future runs. That new export was not used or qualified by the retained episode.

No recorder-native window title matched the owned tab, and existing Chrome media
UI was preserved. No Chrome footage or popup/menu qualification follows. Only
the small owned native control was recorded:183 exact mux/source stamps, zero
journal loss. Six terminal receipts have five verified and one unknown outcome,
all cleanup complete, audit uncovered zero. The shared Chrome/provider coverage
fact reports failure, with provider version unknown. Native fixture/tab absent,
owned loopback server exited and exact session closed.

Actual service input queries return zero events and zero gap notifications for
the browser action, but retain one closed semantic action snapshot. The native
control returns four events and two action snapshots. Both still declare input
delivery completeness unproven. This qualifies a useful fallback: retain the
source-owned action context even when OS events are absent. A closed snapshot
does not invent a missing captured begin update or independently verify delivery.

Agents should preserve provider-specific semantic action marks and observed app
milestones alongside global telemetry. A DOM-delivered effect may need an
agent-authored cue; do not fabricate an OS event, clock, pointer coordinate or
per-key success to fill the gap. Event trust alone would not authenticate an actor
even if available. The current shared app-learning planner can return this scoped
failed capability; a current native tap grant does not override it.

The first schedule rejected unsupported `shows_cursor` before acceptance and
was corrected to `show_cursor`. The launch-control receipt also contains a
caller provider-label error (`browser-cua` for a native CUA call), explicitly
preserved in its typed outcome. Neither error justifies rewriting timestamps,
replaying an unknown mutation or claiming authenticated provider identity.
